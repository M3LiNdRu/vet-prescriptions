# Implementation Plan: Veterinary Prescription Generator

**Branch**: `001-vet-prescription` | **Date**: 2026-05-17 | **Spec**: specs/001-vet-prescription/spec.md

## Summary

Build a veterinary prescription generator with a React frontend, .NET 10 REST API (CQRS + vertical slices, no MediatR), MongoDB for persistence, and Docker Compose for local development. Semantic release on every push to `master` via Conventional Commits.

## Technical Context

**Language/Version**: C# / .NET 10 (backend), TypeScript / React 19 (frontend)
**Primary Dependencies**: FluentValidation.AspNetCore, QuestPDF (PDF generation), MongoDB.Driver, Serilog.AspNetCore, Swashbuckle.AspNetCore, Vite + React, TailwindCSS
**Storage**: MongoDB (local container)
**Testing**: xUnit + Moq (unit tests), Microsoft.AspNetCore.Mvc.Testing (integration tests), Vitest + React Testing Library (frontend unit tests). Minimum 80% coverage enforced on both backend and frontend.
**API Spec**: OpenAPI 3.1 (all endpoints), Arazzo 1.0 (workflow scenarios: create prescription → generate PDF)
**Target Platform**: Any modern browser (laptop, desktop, mobile phone, tablet) — mobile-first responsive UI. Backend hosted via Docker Compose.
**Project Type**: Web app (REST API + SPA)
**Performance Goals**: PDF generation < 3 seconds
**Constraints**: Fully offline, no cloud dependencies, no MediatR

## Constitution Check

- ✅ Document-first: PDF generation is P1 and drives the entire design
- ✅ Data integrity: FluentValidation runs inside each Handler before any persistence or PDF generation
- ✅ Simplicity: No MediatR, no pipeline behaviours — validation and logging are direct calls inside the Handler
- ✅ Offline-capable: All containers run locally, no external calls
- ✅ Regulatory compliance: PDF layout follows Catalan/Spanish veterinary prescription format (Art. 105.5, Regulation EU 2019/6)
- ✅ Observability: Serilog natural-language audit log written directly inside each Handler after successful execution
- ✅ Quality: 80% coverage enforced on backend and frontend, unit + integration test projects scaffolded from day one
- ✅ API Spec: OpenAPI 3.1 + Arazzo 1.0 written before or alongside each endpoint
- ✅ Release: Conventional Commits + semantic-release on `master`

## Key Design Decisions

### CQRS without MediatR
- No mediator framework. Each slice has a Handler class that is injected directly by ASP.NET Core DI.
- The Handler is responsible for: (1) validating the request via FluentValidation, (2) executing the use case via the Repository, (3) writing the natural-language audit log via Serilog.
- Commands mutate state (Create, Save). Queries read state (GetById, List, GeneratePdf). The distinction is in naming and HTTP verb, not in a framework abstraction.

### Vertical Slices
- Each use case owns its Endpoint + Handler + Repository. No shared repository interfaces.
- Slices reference Domain entities but do not share infrastructure beyond `MongoDbContext`.
- Validation lives inside the Handler using FluentValidation inline (no separate Validator file per slice — keeps it simple).

### PDF Generation
- `GeneratePdfHandler` fetches the prescription from MongoDB, builds a QuestPDF document, and returns the byte stream.
- The endpoint returns `application/pdf` directly — the browser downloads it on both desktop and mobile.
- Signature area: blank line for physical signing, typed vet name printed beneath it.

### Domain Project
- Pure C# classes: `Prescription`, `Vet`, `Owner`, `Patient`, `PrescriptionItem`.
- No MongoDB attributes or framework dependencies in Domain.
- Mapping between Domain entities and MongoDB documents happens inside each Repository.

### Audit Logging
- Each Handler calls `_logger.LogInformation(...)` directly after successful execution with a natural-language message.
- Example: `"Veterinary {VetName} issued prescription {PrescriptionNumber}"`, `"Veterinary {VetName} printed a copy of prescription {PrescriptionNumber}"`.

### Testing Strategy
- **Backend unit tests** (xUnit + Moq): one test class per Handler. Repository is mocked. FluentValidation is tested inline.
- **Backend integration tests** (Mvc.Testing): one test class per endpoint slice. Uses `TestWebApplicationFactory` with a real MongoDB test database.
- **Frontend unit tests** (Vitest + React Testing Library): one test file per feature component (`CreatePrescriptionForm`, `VetProfileForm`, `PrescriptionListItem`, etc.). Tests cover rendering, user interactions, and API call behaviour with mocked `api.ts`. `@testing-library/user-event` for simulating real user interactions.
- Coverage threshold of 80% enforced on backend via `coverlet` (`dotnet test --collect:"XPlat Code Coverage"`) and on frontend via `vitest --coverage` (v8 provider).

### OpenAPI & Arazzo
- `api-specs/openapi.yaml` is the single source of truth for all endpoint contracts.
- `api-specs/arazzo.yaml` describes the create prescription → download PDF workflow.
- Swagger UI served at `/swagger` in development.

### Semantic Release
- `.releaserc.json` configures `semantic-release` with plugins: `@semantic-release/commit-analyzer`, `@semantic-release/release-notes-generator`, `@semantic-release/changelog`, `@semantic-release/git`.
- Every push to `master` runs semantic-release in CI: calculates next version from Conventional Commits, updates `CHANGELOG.md`, creates a git tag.
- Commit types: `feat` → minor, `fix`/`perf` → patch, `BREAKING CHANGE` footer → major.
